# Feature 34 — Rule-based job recommendations

## 1. Goal / non-goals

**Goal:** Give a signed-in job seeker a "Recommended for you" list of published jobs, ranked by a **documented, deterministic, explainable** set of rules, with a human-readable reason attached to every recommendation. The candidate opens a job through the existing Feature 17 detail page and applies through the existing Feature 21 flow. Nothing about the feature depends on AI, an external provider, a subscription, or local model hardware.

**In scope:**

- A candidate-facing recommendations page inside the existing `candidate.` route group, backed by a server-side rule engine.
- Five documented matching signals (§4): normalized skill overlap, job category, experience level, location, workplace arrangement.
- A per-recommendation reason list generated by the **same** code path that produces the score, so a reason can never disagree with the score (§4.6).
- The candidate-side data this feature needs but the repository does not yet have: three explicit preference columns, a normalized location token, a structured job-skills list, an admin-managed years→experience-level mapping, and two derived skill-index tables (§8).
- A useful fallback state (recent eligible jobs) when the candidate has stated no signal, or when the stated signals match nothing (§2.3).
- Bounded, index-friendly queries with a measured candidate pool (§9).
- No new npm or composer dependency, no AI/embedding/vector infrastructure, no external API, no queue, no cache.

**Non-goals (deliberate, with reasons):**

- **Any AI, ML, embeddings, vector database, LLM API, or local model.** Forbidden by `project-overview.md` §"Later capabilities and product boundaries". The matching rules in §4 are plain arithmetic over indexed columns.
- **Employer-facing candidate scoring or ranking.** Forbidden by the roadmap's out-of-scope list. No employer surface, no employer API, no signal about a candidate reaches `employer/*` or `admin/*`.
- **Automated candidate screening, auto-rejection, auto-ranking for hiring, or any scoring that feeds an application status change.** Application status remains governed solely by the Feature 24 transition matrix.
- **A skill catalogue (admin-managed) + pivot.** The repository already stores candidate skills as a free-text JSON array (`candidate_profiles.skills`). A matching job-side column mirrors that exactly and avoids inventing a new admin configuration surface (Features 5–9 catalogue pattern) that the roadmap does not ask for.
- **A `recommendations` persistence table, impression tracking, "because you viewed" graph, or collaborative filtering.** Recommendations are computed on read from current data; persisting them would go stale the moment a job closes.
- **A new permission slug (`recommendations.view`).** The route already sits behind `auth` + `role:job_seeker` (§5). Adding a platform permission for a page only one role can reach would be ceremony, and per the durable notes in `memory.md` every new platform permission touches four places.
- **Replacing or changing public search (Feature 16), saved searches (Feature 29), or the public job listing.** This feature is additive. It reuses `JobSearchService::visibility()` and does not modify its behaviour.
- **Writing recommendation views to the audit log (Feature 31).** A candidate reading their own personalised list is neither a security nor an administrative event. No new `AuditAction` value is added. (Contrast Feature 32, where `analytics.viewed` _was_ audited because admin analytics reads are administrative.)
- **Notifications about recommendations.** Alerting belongs to Feature 29's saved-search mechanism; this feature sends nothing.

## 2. User-visible behavior and acceptance criteria

### 2.1 Signed-in candidate with a stated signal

**AC-R1.** `GET /candidate/recommendations` returns a paginated list of published jobs ranked by the rules in §4.

**AC-R2.** Every recommendation carries a `match_score` (0–100) and a non-empty `reasons` array. A reason is emitted **only** when its signal earned points; every signal that earned points emits exactly one reason. A job with zero applicable signals is not recommended at all (it cannot be scored) and does not appear.

**AC-R3.** The reason text names the concrete matched values, e.g. _"Matches 4 of the job's listed skills — PHP, Laravel, MySQL, Redis"_, _"Software Engineering — matches your preferred category"_, _"Remote — matches your preferred work arrangement"_. Reason text is generated server-side; the frontend renders it verbatim.

**AC-R4.** Ordering is deterministic: `match_score DESC`, then `created_at DESC`, then `job id ASC`. Two identical requests against identical data return an identical ordering.

**AC-R5.** Each recommendation links to the existing public job detail page (`/jobs/{job}`) and from there into the existing application flow. The feature adds **no** new apply endpoint and does not bypass Feature 21's validation.

**AC-R6.** A recommendation never exposes another candidate's data, an employer-private field, an internal moderation note (`rejection_reason`), an application count, a resume, or any candidate profile field other than the requester's own.

**AC-R7.** Jobs the candidate has already applied to remain visible, carry an `Applied` badge, and are **not** re-scored (applied-ness is not a fit signal).

### 2.2 Signed-in candidate with no stated signal

**AC-R8.** A candidate with no skills, no preferences and no location sees the **fallback** state: the most recent eligible jobs, clearly labelled _"Showing recent jobs — complete your profile to get personalised recommendations."_, plus a link to the profile editor.

**AC-R9.** A candidate who has stated signals but whose signals match nothing also receives the fallback state (not a blank page).

**AC-R10.** The response always includes a `mode` prop (`matched` | `fallback`) so the UI never has to infer which state it is in.

### 2.3 Eligibility (what may be recommended at all)

**AC-R11.** A job is eligible only if **all** hold:

1. `status = 'published'`
2. its company `is_active = true`
3. its company owner is an approved employer (`EmployerStatus::Approved`)
4. `application_deadline` is null or not in the past

Conditions 1–3 are exactly `JobSearchService::visibility()` and **must** be reused, not re-implemented. Condition 4 is the "accepting applications" rule already applied by `Candidate\JobApplicationController::create()`.

**AC-R12.** Drafts, pending-review, rejected and closed jobs, jobs of inactive companies, jobs of unapproved/suspended employers, and jobs past their application deadline never appear — not in matched mode, not in fallback mode.

### 2.4 Profile and job authoring

**AC-R13.** The candidate profile editor gains an optional **Job preferences** section: preferred category, preferred experience level, preferred workplace arrangement. Each is independently optional.

**AC-R14.** The employer job editor gains an optional **Skills** field, accepting up to 30 free-text entries of up to 50 characters, mirroring the existing candidate `skills` rule exactly.

**AC-R15.** The admin experience-level editor gains an optional **Minimum years** field, defining the lower bound of that level's band.

### 2.5 Cross-cutting

**AC-R16.** No AI service, paid provider, external API, or local model is introduced. `composer.json` and `package.json` are unchanged.

**AC-R17.** All list data is server-driven and paginated. No client-side filtering or sorting of a large result set.

**AC-R18.** TypeScript remains strict: no `any` in the new types or components.

## 3. Assumptions / questions

### 3.1 Decisions carried from the design discussion (accepted)

These were proposed and accepted during the Feature 34 design conversation and are written here as binding design decisions. They may still be overruled at spec review.

| #   | Decision                                                                                                                                                                                                                                                           |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D1  | Candidate preferences are stored as **three dedicated nullable FK columns** on `candidate_profiles`, not inferred from `headline` and not reused from saved searches. A stated preference is the only thing that can honestly produce a reason.                    |
| D2  | Job skills are a **free-text JSON array** on `job_postings`, mirroring `candidate_profiles.skills`. No platform skill catalogue.                                                                                                                                   |
| D3  | Skill matching uses **two derived pivot tables** (`candidate_skills`, `job_skills`) so the match is one portable indexed join on both MySQL and SQLite.                                                                                                            |
| D4  | Years → experience-level mapping is an **admin-managed `min_years` column** on `experience_levels`, not a hard-coded map in PHP.                                                                                                                                   |
| D5  | Location matching uses a **derived `location_city` token** on both tables, produced by one shared normaliser.                                                                                                                                                      |
| D6  | Already-applied jobs **remain in the list** with an `Applied` badge and are not re-scored.                                                                                                                                                                         |
| D7  | Remote jobs (`location_city` null) are **location-agnostic**: the location signal is not applicable to them, and the workplace signal carries the remote preference instead.                                                                                       |
| D8  | A job with **no listed skills** has **no skill signal** (the signal is simply not applicable to that job). Tokenising `requirements` as a fallback was considered and **rejected** — it produces false positives that cannot produce a truthful reason (see §4.3). |
| D9  | Backfilling `job_postings.skills` for pre-existing jobs is an **optional Artisan command**, deliberately **not** a data migration.                                                                                                                                 |

### 3.2 Non-blocking assumptions

- **A1.** The three preference columns are nullable and a null value means _"no preference"_, which is **neutral**, never a mismatch. A candidate with no preferences must still receive recommendations based on their other signals.
- **A2.** "Experience level" for a candidate means _"the level I am targeting"_, not _"the level I currently occupy"_. The candidate's **current** level is computed from their work history (§4.4) and is used only as a fallback when no target level is stated.
- **A3.** Recommendation page size is **12** per page, matching `PublicJobController` (`paginate(12)`).
- **A4.** The candidate pool size is **200** jobs (§9.4), chosen as a deliberate, measurable bound in the spirit of the Feature 32 "measure first" rule.
- **A5.** "Experience" for the years calculation is measured from `candidate_experiences` only. `candidate_educations` contributes nothing (internships, part-time study and career breaks make education dates a poor proxy, and Feature 18's education rows have no `is_current` flag).
- **A6.** The skill alias map (§4.2) is a small, static, unit-tested dictionary in code. It is not admin-managed: it is a normalisation dictionary, not a catalogue of platform vocabulary.

### 3.3 Open questions (non-blocking)

- **Q1.** Should the recommendation page also be reachable from the candidate dashboard as a preview card (top 3) in addition to a full page? _Assumption: yes, a dashboard link and a small preview are added; this is presentation only and does not change the route contract._
- **Q2.** Should the employer job form make skills **required** for a job to be submitted for review? _Assumption: no — optional, to avoid blocking the existing Feature 14 submission flow. Jobs without skills fall back to D8._

Neither question blocks implementation of the vertical slice.

## 4. Matching rule dictionary (the formulas)

This section is the contract. Every formula is deterministic and unit-testable. All weights are fixed constants in code, documented here, and asserted by tests.

### 4.1 Candidate signals (the input side)

| Signal                  | Source                                                                             | Normalised form                  |
| ----------------------- | ---------------------------------------------------------------------------------- | -------------------------------- |
| Skills                  | `candidate_profiles.skills` (JSON) → `candidate_skills.skill`                      | canonical lowercase tokens, §4.2 |
| Preferred category      | `candidate_profiles.preferred_category_id`                                         | config id                        |
| Target experience level | `candidate_profiles.preferred_experience_level_id`, else derived from years (§4.4) | config id + band rank            |
| Location                | `candidate_profiles.location_city`                                                 | canonical city token, §4.2       |
| Preferred workplace     | `candidate_profiles.preferred_workplace_arrangement_id`                            | config id                        |

### 4.2 Normalisation

**`App\Support\SkillNormalizer`**

- `normalize(string $raw): string` — trim → collapse internal whitespace → lowercase → strip surrounding punctuation → apply the alias map → truncate to 60 characters.
- `normalizeList(array $raw): array` — normalise each entry, drop empties, de-duplicate, sort ascending (stable storage order).
- Alias map (static, unit-tested, illustrative): `js`→`javascript`, `nodejs`→`node.js`, `node js`→`node.js`, `reactjs`→`react.js`, `postgres`→`postgresql`, `golang`→`go`, `c#`→`csharp`, `c++`→`cpp`, `rest`→`rest api`, `restful`→`rest api`. The map is a constant array in the class; it is never read from the request.
- The **display** form of a skill (as the candidate typed it, e.g. `"PHP"`) is preserved in `candidate_profiles.skills`; only the pivot holds the canonical form. Reason text renders the candidate's display form.

**`App\Support\LocationNormalizer`**

- `city(?string $raw): ?string` — trim → lowercase → take the segment before the first comma → collapse whitespace → strip characters other than letters, digits, spaces and hyphens → return `null` when the result is empty **or** the input is one of the "location-agnostic" tokens (`remote`, `anywhere`, `worldwide`, `n/a`, `work from home`, `wfh`, `-`, `—`).
- Examples: `"Pune, India"` → `pune`; `"Pune"` → `pune`; `"  REMOTE "` → `null`; `"Bengaluru, Karnataka, India"` → `bengaluru`.
- `location_city` is **derived**, never mass-assignable: it is written only by the `location` mutator (§8.4).

### 4.3 The five signals, weights, and point formulas

| Signal               | Weight | Applicable when                                                                                          | Points earned                                                                                 |
| -------------------- | ------ | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| **Skill overlap**    | 40     | the job has ≥ 1 skill **and** the candidate has ≥ 1 skill                                                | `40 × (matched ÷ jobSkillCount)`, floored, capped at 40                                       |
| **Category**         | 20     | the candidate stated `preferred_category_id`                                                             | 20 if `job.category_id` equals the preference, else 0                                         |
| **Experience level** | 20     | the job has `experience_level_id` **and** the candidate's target level resolves                          | 20 if the job's band rank equals the target's; 10 if the rank difference is exactly 1; else 0 |
| **Location**         | 10     | the candidate has `location_city` **and** the job has `location_city`                                    | 10 if equal, else 0                                                                           |
| **Workplace**        | 10     | the candidate stated `preferred_workplace_arrangement_id` **and** the job has `workplace_arrangement_id` | 10 if equal, else 0                                                                           |

**Job skill set.** A job's skills are `job_skills.skill`. Per **D8**, when a job has **no** listed skills the skill signal is **not applicable** to that job — it is _not_ tokenised from `requirements`. (The earlier tokenisation idea is dropped: it produced false positives such as `c` matching every paragraph and `go` matching "going to", and a fuzzy match cannot produce a truthful reason. A job with no listed skills simply has no skill signal, and is still recommendable on its other signals. Q2's "optional" answer follows from this.)

**Job skill count (`jobSkillCount`).** The number of distinct skills in the job's `job_skills` rows.

**Matched skills.** The intersection of the candidate's canonical skill set and the job's canonical skill set. Reason text lists them using the candidate's display spelling, ordered by the canonical form (stable).

### 4.4 Candidate years of experience

**`App\Support\ExperienceCalculator::years(CandidateProfile $profile): float`**

- Each `candidate_experiences` row contributes the interval `[start_date, end_date ?? today]`.
- Rows with a null `start_date` are ignored (they cannot be placed on a timeline).
- A `start_date` in the future is ignored.
- Overlapping intervals are **merged** before summing, so two concurrent roles do not double-count.
- The result is the merged total in months ÷ 12, rounded to one decimal, clamped to ≥ 0.
- Worked example: `2021-06-01 → present` plus `2023-01-01 → 2023-09-01` ⇒ merged `2021-06-01 → present` ⇒ **5.0 years** (not 5.75).

**Derived candidate level.** The level whose `min_years` is the greatest value **not exceeding** the candidate's years. Ties on `min_years` are broken by the greatest `sort_order`. If no level has `min_years` set, or the candidate has no experiences, the candidate's level is **unresolvable** and the experience-level signal is not applicable (unless a target level is stated).

**Target level.** `preferred_experience_level_id` when set; otherwise the derived level. A stated target always wins.

**Band comparison.** By **band rank**, not by the raw `sort_order` value.

`experience_levels.sort_order` is the intended ordering but it is **not unique**: the admin form accepts any integer in `0–9999` and the factory defaults to `0`, so several distinct levels can legitimately share a sort order. Comparing raw sort orders would then report unrelated levels as the same band — a candidate targeting "3 year" would be told that a "1 year" role "matches your target level".

The rank is therefore derived from `(sort_order, id)`: all levels are ordered by `sort_order` ascending and then by `id` ascending, and each receives a 1-based rank. Ties are broken by the primary key, which is the order the levels were created in. The rank is unique, deterministic, and preserves the intended ordering. A rank difference of 0 is an exact band match; a difference of 1 is an adjacent band (worth half the signal's points); a difference ≥ 2 is no match.

The ranking is rebuilt on every request rather than memoised, so a long-lived container can never serve a stale ordering.

### 4.5 Score

```
earned        = skillPoints + categoryPoints + levelPoints + locationPoints + workplacePoints
applicableSum = sum of the weights of the signals that are applicable to this job
match_score   = applicableSum > 0 ? round(100 × earned ÷ applicableSum) : null
```

A job whose `applicableSum` is 0 has **no** score and is **not recommended** in matched mode. `match_score` is normalised over the signals that actually apply, so a candidate who has stated only skills still receives a meaningful 0–100 range instead of a score capped at 40 %.

### 4.6 Reasons

One reason is emitted per signal that earned points, and only for those signals.

| `code`                   | `detail` template                                                                              | `values`                    |
| ------------------------ | ---------------------------------------------------------------------------------------------- | --------------------------- |
| `skill_overlap`          | `"Matches {matched} of the job's {total} listed skills"`                                       | matched skill display names |
| `category_match`         | `"{category} — matches your preferred category"`                                               | `[]`                        |
| `experience_level_match` | `"{level} — matches your target level"` or `"{level} — one level from your target ({target})"` | `[]`                        |
| `location_match`         | `"{city} — matches your location"`                                                             | `[]`                        |
| `workplace_match`        | `"{arrangement} — matches your preferred work arrangement"`                                    | `[]`                        |

Reasons are produced by `RecommendationScorer`, the **same** class that produces the score. There is no second, display-only computation. The invariant _"a reason exists if and only if its signal earned points"_ is asserted directly by tests (§12.4).

### 4.7 The candidate-side eligibility filter (the bounded narrowing)

Before scoring, the pool is narrowed to jobs that match **at least one** stated signal. Each term is omitted when the corresponding input is absent:

```
(candidate has skills AND job has ≥ 1 of the candidate's canonical skills)
OR (candidate stated preferred_category AND job.category_id = preferred_category)
OR (candidate target level resolves AND the job's level rank is within 1 of the target's rank)
OR (candidate has location_city AND job.location_city = candidate.location_city)
OR (candidate stated preferred_workplace AND job.workplace_arrangement_id = preferred_workplace)
```

A preference is a **scoring** input, not an exclusion filter: a job in a different category still appears (and scores 0 on the category signal) if it matches on skills. The filter only decides _which jobs enter the pool_; §4.3 decides _how they rank_.

If **no** term applies (the candidate has stated nothing), the matched query is not run at all and the fallback is served directly (§2.2).

## 5. Routes and access boundary

### 5.1 Route

Added inside the existing group at `routes/web.php:177` (`prefix('candidate')`, `name('candidate.')`, `middleware(['role:job_seeker'])`):

| Method | URI                          | Name                              | Controller                                                      | Middleware                |
| ------ | ---------------------------- | --------------------------------- | --------------------------------------------------------------- | ------------------------- |
| GET    | `/candidate/recommendations` | `candidate.recommendations.index` | `App\Http\Controllers\Candidate\RecommendationController@index` | `auth`, `role:job_seeker` |

No new middleware is introduced. The `candidate.` group already carries `auth` (from the enclosing authenticated group) and `role:job_seeker`.

### 5.2 Access boundary rationale

- **Route/group middleware** is the access boundary: a guest is redirected to login; an employer or administrator is rejected by `role:job_seeker` (403).
- **No Policy is added.** The resource being protected is _the requester's own recommendation list_, which is derived from the requester's own profile and contains no model that needs instance-level authorization. `SavedSearchPolicy` is the closest precedent for a candidate-owned read surface; the deciding factor here is that the recommendations page exposes **no** first-class model to authorize — it is a derived read of the current user's own profile against public job data. A Policy would be a meaningless abstraction (AGENTS.md §3: "Internal value objects and purely technical models need not receive a meaningless Policy").

    The **job-side** authorisation that _does_ matter is the visibility gate (`JobSearchService::visibility()`), which is a query concern, not a Policy concern — the same as `PublicJobController@index`.

- The **employer** surface is unchanged: no route, no controller, no prop, no audit entry. No candidate signal is ever written to an employer-visible table.

## 6. Policy actions and dynamic role/permission resolution

### 6.1 No new permission, no new role

This feature adds **no** platform permission and **no** company-scoped permission.

- The candidate page is inside the existing `role:job_seeker` group. Per the durable notes in `memory.md`, adding a platform permission touches four places (`PermissionSlug` enum, `AuthorizationSeeder` display map **and** the `$platformAdminPermissionSlugs` allow-list, the hard-coded counts in `tests/Feature/Authorization/AuthorizationCatalogueTest.php`, and the catalogue table in `docs/authorization.md`). None of that is justified for a page only one role can reach.
- The employer-side change is _content_, not permission: an employer editing their own job adds skills to that job. It reuses the **existing** `JobPolicy` (`update`) already enforced by `Employer\JobController@update()` → `$this->authorize('update', $job)`. No new Policy action is introduced, so the owner/company scoping of job editing is unchanged and still enforced.
- The admin-side change is _content_: adding `min_years` to an experience level reuses the **existing** `ExperienceLevelPolicy` actions already enforced by `Admin\ExperienceLevelController`.

### 6.2 Existing policies that remain the enforcement point

| Policy / rule                               | Where it applies after this change                                                  |
| ------------------------------------------- | ----------------------------------------------------------------------------------- |
| `JobPolicy::update`                         | employer editing a job's skills — unchanged, still company-scoped                   |
| `ExperienceLevelPolicy` (`update`/`create`) | admin setting `min_years` — unchanged                                               |
| `CandidateProfilePolicy` (`update`)         | candidate editing their own profile and preferences — unchanged, still owner-scoped |
| `role:job_seeker` middleware                | the recommendations route — unchanged                                               |

### 6.3 Client-supplied identifiers

The preference columns are validated with `exists:` rules against the configuration tables (§7.1) and are written only from the validated payload by `CandidateProfileService::update()` — never from `$request->all()`. A candidate may only set a preference to a **configuration** id that exists; there is no user id, company id, job id or role id in this feature's write path.

## 7. Form Requests and validation

### 7.1 `App\Http\Requests\Candidate\UpdateCandidateProfileRequest` (modified)

Extends the existing request. The existing `prepareForValidation()` normalisation block is extended (not duplicated) and `profileData()` is extended with three keys.

```php
'preferred_category_id' => ['nullable', 'integer', 'exists:job_categories,id'],
'preferred_experience_level_id' => ['nullable', 'integer', 'exists:experience_levels,id'],
'preferred_workplace_arrangement_id' => ['nullable', 'integer', 'exists:workplace_arrangements,id'],
```

- The `exists:` pattern is copied from `StoreSavedSearchRequest` (the established convention for these configuration ids in this repository).
- Only **active** configuration options should be selectable for new choices, but an **existing, now-deactivated** option must remain readable and submittable (project rule: "Deactivate an option that is already used rather than deleting history"). Implementation: validate `exists:` plus a `withValidator` check that rejects ids that are **inactive** _unless_ the candidate already holds that id. This mirrors the existing employer job form behaviour for inactive options.
- `profileData()` adds:
    ```php
    'preferred_category_id' => $validated['preferred_category_id'] ?? null,
    'preferred_experience_level_id' => $validated['preferred_experience_level_id'] ?? null,
    'preferred_workplace_arrangement_id' => $validated['preferred_workplace_arrangement_id'] ?? null,
    ```
- `skills` rules are **unchanged** (`nullable|array|max:30`, `skills.*` `string|max:50`) — the candidate skill contract is already correct.

### 7.2 `App\Http\Requests\Employer\StoreJobRequest` / `UpdateJobRequest` (modified)

```php
'skills' => ['nullable', 'array', 'max:30'],
'skills.*' => ['string', 'max:50'],
```

- `jobData()` adds `'skills' => array_values($validated['skills'] ?? [])`.
- The request already normalises strings in `prepareForValidation()`; the same trim-and-drop-empty treatment is applied to `skills` entries.
- **No new authorisation surface**: `skills` is content on a job the employer already owns. `JobPolicy::update` still gates the write, and `Employer\JobController` resolves the company through `Company::forManagingUser($user)` — the existing IDOR defence is untouched.

### 7.3 `App\Http\Requests\Admin\StoreExperienceLevelRequest` / `UpdateExperienceLevelRequest` (modified)

```php
'min_years' => ['nullable', 'integer', 'min:0', 'max:60'],
```

`experienceLevelData()` adds `'min_years' => $data['min_years'] ?? null`.

### 7.4 No Form Request for the recommendations route

`GET /candidate/recommendations` takes **no** input beyond pagination. It is a read endpoint with no user-supplied filters, so no Form Request is created (AGENTS.md §3: simple read, no ceremony). Page navigation is handled by the shared `Pagination` component using the paginator's own URLs.

```
  id                bigIncrements
  candidate_profile_id  foreignId -> candidate_profiles, cascadeOnDelete

  timestamps
  UNIQUE (candidate_profile_id, skill)          -- candidate_skills_profile_skill_unique
  INDEX  (skill, candidate_profile_id)          -- candidate_skills_skill_profile_idx

job_skills
  id                bigIncrements
  job_posting_id    foreignId -> job_postings, cascadeOnDelete
  skill             string(60)
  timestamps
  UNIQUE (job_posting_id, skill)                -- job_skills_posting_skill_unique
  INDEX  (skill, job_posting_id)                -- job_skills_skill_posting_idx
```

- The `UNIQUE` constraint prevents duplicate skills for the same owner and gives the "delete-then-insert" sync a safe target.
- The `(skill, owner)` index is the **leftmost-prefix** match for the matching query, which filters on `skill` and joins to the owner.
- `timestamps` are included for consistency with every other pivot in this repository (`saved_search_alerts`, `company_members`, `job_application_answers`). The rows are fully rebuilt on each sync, so the timestamps carry no history meaning.
- **Deletion semantics:** `cascadeOnDelete` — deleting a job or a candidate profile removes its skill-index rows automatically. No orphan rows. (Note: `job_postings` are never hard-deleted in this application — closing sets `status = 'closed'` — so the job-side cascade is a safety net, not a normal path.)

### 8.4 Model changes

| Model              | Change                                                                                                                                                                                                                                                                                                                                         |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CandidateProfile` | `$fillable` gains the three `preferred_*` ids; `location_city` is **not** fillable; `skills` cast stays `'array'`; new relations `preferredCategory()`, `preferredExperienceLevel()`, `preferredWorkplaceArrangement()`, `skillTags()` (`hasMany CandidateSkill`); a `location` attribute mutator writes `location` + `location_city` together |
| `Job`              | `$fillable` gains `skills`; `skills` cast `'array'`; `location_city` **not** fillable; new relation `skillTags()` (`hasMany JobSkill`); `location` attribute mutator writes `location` + `location_city` together                                                                                                                              |
| `ExperienceLevel`  | `$fillable` gains `min_years`; cast `'integer'`; no new relations                                                                                                                                                                                                                                                                              |
| `CandidateSkill`   | **new** — pivot model, `$fillable = ['candidate_profile_id','skill']`, `belongsTo` the profile                                                                                                                                                                                                                                                 |
| `JobSkill`         | **new** — pivot model, `$fillable = ['job_posting_id','skill']`, `belongsTo` the job                                                                                                                                                                                                                                                           |

**Why the relation names are `skillTags`:** `CandidateProfile::skills` and `Job::skills` are already taken by the JSON column. Eloquent cannot have a relation and an attribute with the same name.

**`location` mutator.** Implemented as an Eloquent `Attribute` mutator whose `set` returns an array, so the derived token can never be set independently:

```php
protected function location(): Attribute
{
    return Attribute::make(
        set: fn (?string $value): array => [
            'location' => $value,
            'location_city' => LocationNormalizer::city($value),
        ],
    );
}
```

Because `location_city` is absent from `$fillable`, a client cannot forge it through mass assignment; the mutator is the only writer.

### 8.5 Deletion / deactivation semantics

- `preferred_*` columns use **`nullOnDelete`**, deliberately departing from the `restrictOnDelete` used on `job_postings.category_id` and `saved_searches.category_id`. Rationale: a preference is a nullable statement of intent where _null is a meaningful value_ ("no preference"). Blocking the deletion of a catalogue entry because one candidate mentioned it would be a defect, not a safeguard. Documented here as an intentional, reviewed deviation from the surrounding convention.
- Configuration options are **deactivated, not deleted**, by the platform (Features 5–9). If an option _is_ deleted, the candidate's preference becomes `null` (neutral) rather than erroring.
- A job's `skills` and `location_city` are cleared by clearing `skills` / `location`. A job with zero skills simply has no skill signal (§4.3).
- Deleting a job or a candidate profile removes the derived skill-index rows via `cascadeOnDelete`.

### 8.6 Indexes

Added by `2026_11_15_000001_add_recommendation_supporting_indexes.php`:

| Index                                       | Columns                                         | Rationale                                                          |
| ------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------ |
| `job_skills_skill_posting_idx`              | `job_skills(skill, job_posting_id)`             | the matching join: filter on `skill`, join to the job              |
| `candidate_skills_skill_profile_idx`        | `candidate_skills(skill, candidate_profile_id)` | the candidate-side lookup by skill                                 |
| `job_postings_location_city_idx`            | `job_postings(location_city)`                   | the location term of the §4.7 filter                               |
| `job_postings_category_id_idx`              | `job_postings(category_id)`                     | the category term of the §4.7 filter — **SQLite only** (see below) |
| `job_postings_experience_level_id_idx`      | `job_postings(experience_level_id)`             | the level term — SQLite only                                       |
| `job_postings_workplace_arrangement_id_idx` | `job_postings(workplace_arrangement_id)`        | the workplace term — SQLite only                                   |

**The InnoDB FK-index rule.** MySQL/InnoDB owns foreign-key backing indexes: it silently drops a redundant FK index when a covering index is added, and refuses to drop an index a FK depends on. `category_id`, `experience_level_id` and `workplace_arrangement_id` are FK columns, so **MySQL already indexes them** while SQLite does not.

The migration therefore uses the **exact pattern** established in `database/migrations/2026_11_14_000000_add_analytics_supporting_indexes.php`:

- a private `addIndex(string $table, string $name, array $columns)` helper guarded by `Schema::hasIndex()`;
- a private `dropIndex(string $table, string $name)` helper guarded by `Schema::hasIndex()`;
- a private `usesForeignKeyIndexes(): bool` helper checking `Schema::getConnection()->getDriverName() === 'mysql'`;
- the three FK-column indexes are added **only when the driver does not provide FK backing indexes**, and `down()` restores them when the driver does.

`up()` and `down()` are both idempotent.

**No index on `candidate_profiles.location_city`.** The candidate's city is only ever read through `user_id` (which already has a unique index). It is never used as a query filter, so an index there would be pure write cost.

### 8.7 Keeping the skill index in sync

`App\Services\Recommendation\SkillIndexService` is the **single writer** of both pivot tables:

- `syncProfile(CandidateProfile $profile): void` — deletes the profile's `candidate_skills` rows and re-inserts the normalised set.
- `syncJob(Job $job): void` — deletes the job's `job_skills` rows and re-inserts the normalised set.

**Wiring.** The sync is invoked from an Eloquent `saved` event on `CandidateProfile` and `Job`, gated on `wasChanged('skills')` so it runs only when the skill list actually changed. Doing it in the model event rather than in each controller guarantees that **every** write path stays consistent — including `Employer\JobController::store()`/`update()` and `CandidateProfileService::update()` — and that a future write path cannot silently skip the index.

**Atomicity.** The sync runs inside the same transaction as the parent write:

- `CandidateProfileService::update()` already wraps its work in `DB::transaction(...)` — the sync is added inside that closure.
- `Employer\JobController::store()` and `update()` currently have **no** transaction. Both are changed to wrap the job write and the skill sync in `DB::transaction(...)`. This also closes a latent inconsistency: today a job write and its side effects are not atomic.

**Drift is impossible** because the pivot is only ever written by `SkillIndexService`, always from the JSON source of truth, always in the same transaction.

## 9. Query / data payload shape, eager loading, pagination, scale

### 9.1 Query composition

`JobRecommendationService::recommend(User $user)` performs, in order:

1. **Load the candidate profile** — `CandidateProfile` by `user_id`, with `skillTags` and `experiences` eager-loaded. One query each.
2. **Derive the signals** — normalise skills, normalise the location token, resolve the target level (§4.4), read the three preferences.
3. **Decide the mode** — if no §4.7 filter term applies, go straight to the fallback query.
4. **Pool query** — see §9.2.
5. **Score** — `RecommendationScorer::score()` per job, in PHP, using the eager-loaded data.
6. **Sort** — `match_score DESC`, `created_at DESC`, `id ASC`.
7. **Paginate** — slice the current page from the sorted pool and build the paginator metadata.

### 9.2 The pool query

```php
Job::query()
    ->select([...explicit columns...])
    ->with([
        'company:id,name,slug,logo_path',
        'category:id,name,slug',
        'employmentType:id,name,slug',
        'workplaceArrangement:id,name,slug',
        'experienceLevel:id,name,slug',
        'payPeriod:id,name,slug',
    ])
    ->withCount(['skillTags as matched_skills_count' => fn ($q) => $q->whereIn('skill', $candidateSkills)])
    ->withCount('skillTags as total_skills_count')
    ->published();                                   // status = 'published'
```

then, **reusing the existing service** (`app/Services/JobSearchService.php`):

```php
$searchService->visibility($query);                // company active + owner approved
$query->where(fn ($q) => $q->whereNull('application_deadline')
                          ->orWhere('application_deadline', '>=', today()));
```

then the §4.7 filter as a single `where(function ($q) { ... })` with one OR-term per stated signal, each term omitted when its input is absent:

```php
$query->where(function (Builder $q) use (...) {
    if ($candidateSkills !== []) {
        $q->orWhereHas('skillTags', fn (Builder $sq) => $sq->whereIn('skill', $candidateSkills));
    }
    if ($preferredCategoryId !== null) {
        $q->orWhere('category_id', $preferredCategoryId);
    }
    if ($targetLevelIds !== []) {
        $q->orWhereIn('experience_level_id', $targetLevelIds);
    }
    if ($candidateLocationCity !== null) {
        $q->orWhere('location_city', $candidateLocationCity);
    }
    if ($preferredWorkplaceId !== null) {
        $q->orWhere('workplace_arrangement_id', $preferredWorkplaceId);
    }
});
```

and finally the bound and the ordering:

```php
$pool = $query->orderByDesc('created_at')->orderBy('id')->limit(self::POOL_SIZE)->get();  // POOL_SIZE = 200
```

### 9.3 Why the pool is fetched and scored in PHP

The score and the reasons are produced by **one** class (`RecommendationScorer`). If the score were computed in SQL with `CASE` expressions and the reasons in PHP, the two could drift — and the spec's "explanation accuracy" requirement would rest on an unverified assumption. Scoring the bounded pool in PHP makes that invariant structural: one implementation, one output.

The trade-off is explicit and accepted: the pool is the **200 newest** jobs that match at least one stated signal, and the ranking is _fit-first within that pool_. A very strong match published a long time ago can fall outside the pool. This is recorded as a follow-up (§15) with its trigger condition (measured pool saturation).

### 9.4 Scale considerations

- **Bounded.** The pool is capped at 200 rows per request. The eager loads are `whereIn`-style batch loads (one query per relation, not per row) — no N+1.
- **Indexed.** Every term of the §4.7 filter sits on an indexed column (§8.6); the skill term is an `EXISTS` against `job_skills(skill, job_posting_id)`.
- **Correlated sub-counts, not a join.** `withCount` produces correlated `SELECT COUNT(*)` sub-selects, so the pool query has no join fan-out and no `GROUP BY`, and the row count stays exact.
- **Two bounded extra queries** for the page's 12 jobs: the candidate's saved job ids and the candidate's application job ids, both `whereIn('job_posting_id', $pageJobIds)` — bounded by 12.
- **No unbounded `get()`** anywhere in the read path.
- **Measurement is required, not assumed.** `EXPLAIN` must be run on a seeded dataset for both engines, in the same style as the Feature 32 verification (§13.5). The recorded result goes in §16.

### 9.5 Pagination

- Page size **12** (matching `PublicJobController`).
- Pagination is over the **scored, sorted pool**, so `total` is the number of scored jobs in the pool (≤ 200), and `last_page` = `ceil(total / 12)`.
- The paginator is built as `Illuminate\Pagination\LengthAwarePaginator` with `['path' => request()->url(), 'query' => request()->query()]`, then mapped with `->through(...)` exactly as `SavedJobController` does, so the serialised prop shape is identical to every other candidate list page in the repository.

### 9.6 Inertia props

```php
return Inertia::render('candidate/recommendations', [
    'recommendations' => $paginator->through(fn (RecommendedJob $r): array => [...]),
    'mode' => $mode,                    // 'matched' | 'fallback'
    'profileSummary' => [
        'has_skills'          => bool,
        'has_category'        => bool,
        'has_experience_level'=> bool,
        'has_location'        => bool,
        'has_workplace'       => bool,
        'signals_available'   => int,   // count of stated signals
        'computed_years'      => float|null,
    ],
    'options' => [
        'categories'            => [...active ids + names...],
        'experienceLevels'      => [...],
        'workplaceArrangements' => [...],
    ],
]);
```

`options` is required so the profile editor can render the preference selects without a second round trip. It is bounded (the active configuration catalogues, exactly as `PublicJobController` already returns).

**Nothing else is exposed.** Specifically **not** in the payload: any other candidate's data, `rejection_reason`, application counts, resume metadata, `applications_count`, or the candidate's raw profile JSON.

### 9.7 The fallback query

```php
Job::query()
    ->select([...same columns...])
    ->with([...same relations...])
    ->published();
$searchService->visibility($query);
$query->where(fn ($q) => $q->whereNull('application_deadline')->orWhere('application_deadline', '>=', today()));
$recent = $query->orderByDesc('created_at')->orderBy('id')->limit(self::POOL_SIZE)->get();
```

Fallback rows have `match_score = null` and `reasons = []`, and are presented as "recent jobs", never as "recommended".

## 10. Service / Repository decision

### 10.1 Decision

| Concern                     | Class                      | Location                                                   |
| --------------------------- | -------------------------- | ---------------------------------------------------------- |
| Rule engine + orchestration | `JobRecommendationService` | `app/Services/Recommendation/JobRecommendationService.php` |
| Pure scoring + reasons      | `RecommendationScorer`     | `app/Services/Recommendation/RecommendationScorer.php`     |
| Derived skill-index writer  | `SkillIndexService`        | `app/Services/Recommendation/SkillIndexService.php`        |
| Skill normalisation         | `SkillNormalizer`          | `app/Support/SkillNormalizer.php`                          |
| Location normalisation      | `LocationNormalizer`       | `app/Support/LocationNormalizer.php`                       |
| Years of experience         | `ExperienceCalculator`     | `app/Support/ExperienceCalculator.php`                     |

### 10.2 Rationale

- **A Service is justified here**, unlike simple CRUD. The feature is a multi-step, non-trivial business computation (load profile → derive signals → narrow → score → explain → paginate) with real rules that must be unit-testable and reusable. It is not "a query in a controller".
- **`RecommendationScorer` is separated from `JobRecommendationService`** specifically so the scoring arithmetic can be unit-tested **without a database**, and so the "one implementation produces both the score and the reasons" invariant is structurally enforced.
- **The three `app/Support` classes are pure functions** with no framework dependency beyond `Carbon`/`Illuminate\Support\Str`. They exist because normalisation is used by both the read path (scoring) and the write path (index sync), and duplicating it would let the two drift.
- **No Repository.** The recommendation query is consumed by exactly one controller. A repository layer would be ceremony (AGENTS.md §3: "Simple single-use CRUD? Keep it simple").
- **No new `JobSearchService` method.** The existing `visibility()` and `apply()` are reused as-is. `JobRecommendationService` composes them rather than modifying them, so Feature 16/29 behaviour is unchanged.
- **`app/Support/` is a new top-level directory** — a standard Laravel convention, used here only for pure value helpers. Deliberately minimal: three classes.

### 12.7 Security cases (summary)

- **Authorisation bypass** — the route is behind `role:job_seeker`; no Policy is needed because the read surface exposes no first-class model (§5.2).
- **IDOR** — the recommendations are derived from the **authenticated** user's own profile; there is no id parameter on the route, and no client-supplied user id is read.
- **Mass assignment** — `location_city` is not fillable; the three preference ids are validated with `exists:` and written only from `profileData()`; the pivot models' `$fillable` excludes anything else.
- **Data exposure** — §9.6 lists the exact payload. No `rejection_reason`, no counts, no candidate identity.
- **Injection** — all query inputs are bound parameters; the alias map is a constant; `location_city` is compared with `=`, never interpolated into SQL.
- **Rate limiting** — a read endpoint; no throttling needed, and no write endpoint is added by this feature.

## 13. Risks, rollout / compatibility notes

### 13.1 Security risks

| Risk                                                         | Mitigation                                                                                                                                                   |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A candidate's profile leaks into an employer-visible surface | The feature has **no** employer surface and writes nothing to an employer-visible table. Asserted by test A5 and P4.                                         |
| A client forges `location_city` or a preference id           | `location_city` is not fillable and is written only by the `location` mutator; preference ids are `exists:`-validated and written only from `profileData()`. |
| The recommendations page leaks moderation or applicant data  | The payload is enumerated in §9.6; the selected columns are explicit; `rejection_reason` is never selected.                                                  |
| A stale `job_skills` index produces wrong recommendations    | The index is written by exactly one service, in the same transaction as the parent write, and gated on `wasChanged('skills')`. Sync regression tests S1–S8.  |
| Cross-candidate access                                       | There is no id parameter; the profile is loaded by the authenticated `user_id`.                                                                              |

### 13.2 Performance / scale risks

| Risk                                                                    | Mitigation / trigger                                                                                                                                                                                                      |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The pool query scans too much when a candidate's skills are very common | The §4.7 filter is index-backed on every term; `EXPLAIN` must confirm index use on both engines. If a broad skill set produces a large scan, the remedy is a per-skill posting-frequency cap, **not** a silent full scan. |
| The pool of 200 saturates (many strong matches outside the pool)        | Measurable: record the pool saturation rate in §16. The remedy, if triggered, is a larger pool or a fit-ordered pool — recorded as follow-up F1 (§15).                                                                    |
| 200 rows × eager loads per request                                      | Bounded and batch-loaded; the page size is 12 and only 12 rows are serialised. If the pool is reduced, the cost falls with it.                                                                                            |
| `candidate_skills` / `job_skills` write amplification                   | One delete + one insert per changed skill list, inside the parent transaction. At the current scale this is negligible.                                                                                                   |
| The recommendations page adds latency to a hot path                     | It is a separate page, not the dashboard's default load; the dashboard preview (Q1) renders at most 3 rows and may be capped by a separate smaller pool.                                                                  |

### 13.3 Rollout / compatibility

- **Additive schema only.** Seven columns and two new tables; no existing column changes type, no existing table is dropped or renamed. Existing rows are unaffected (`location_city` is null, `skills` is null, preferences are null).
- **Jobs created before this feature have no skills** → they have no skill signal and are still recommendable on their other signals. **D8** (tokenising `requirements`) was considered and **dropped** in §4.3 because it produces false positives that cannot produce a truthful reason.
- **Candidates created before this feature have no preferences** → their recommendations fall back to skills, location and the derived experience level; if they have none of those, they get the fallback state. No backfill is required and none is performed.
- **Existing behaviour is unchanged.** `JobSearchService::visibility()`/`apply()` are reused, not modified. `SavedSearchPolicy`, `JobPolicy`, `CandidateProfilePolicy` and `ExperienceLevelPolicy` are unchanged.
- **The only behaviour change to an existing endpoint** is that `PUT /candidate/profile`, the employer job endpoints, and the admin experience-level endpoints accept **additional optional** fields. Every pre-existing request remains valid.
- **Migration ordering.** The new migrations are dated `2026_11_15_*`, after the newest existing migration (`2026_11_14_000000`), so they apply last. `up()`/`down()` are idempotent and safe to re-run.
- **MySQL/SQLite parity.** The migration must apply, roll back and re-apply cleanly on **both** engines (the repository's test suite runs on SQLite in-memory; production runs on MySQL).
- **No dependency change.** `composer.json` and `package.json` are untouched. No package-manager action is required or permitted.

## 15. Follow-ups (not built by this feature)

- **F1 — Fit-ordered pool.** The pool is currently the 200 _newest_ jobs matching at least one stated signal, ranked by fit within it. If the measured pool saturation rate (§13.2) shows that strong matches are routinely excluded, the pool selection should become fit-ordered. Trigger: measured evidence.
- **F2 — Skill backfill command.** An optional Artisan command to populate `job_postings.skills` from `requirements` for pre-existing jobs. Deliberately not a data migration (reversibility, lock duration, and the risk of writing wrong data into a content field). Trigger: a real need for legacy jobs to be skill-matchable.
- **F3 — Saved-search preferences as a signal source.** A candidate's saved searches already store category, workplace arrangement and experience level. If a candidate has no explicit preferences, they could be used as a secondary preference source. Explicitly **not** used in this feature (D1): a saved search is a past query, not a stated preference, and the reason text could not be honest about it. Trigger: an explicit product decision.
- **F4 — "Because you applied to…" signal.** A recommendation reason derived from the candidate's own application history. Not built here: it requires a product decision on how application history should influence ranking, and it edges toward the "collaborative filtering" the roadmap excludes.
- **F5 — Employer-facing relevance signals.** Explicitly forbidden by the roadmap for this feature. Any future version requires a separate approved scope with privacy, fairness, transparency and human-oversight requirements.
- **F6 — Recommendation analytics.** Impression/click tracking for the recommendations surface. Not built here; would need its own metric definitions and an audit decision, as in Feature 32.
- **F7 — Pre-existing defect (not in this scope).** `App\Http\Controllers\Employer\JobController::jobPayload()` returns a hard-coded `'applications_count' => 0` (a Feature 15 defect). It is unrelated to recommendations and is deliberately **not** fixed here.

### 16.2 Deviations from the written specification

| #      | Deviation                                                                                                                                                                                     | Reason                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **D1** | The three `candidate_profiles.preferred_*` columns carry **no database-level foreign key**; they are indexed unsigned big integers validated at the application layer.                        | SQLite refuses to `DROP COLUMN` for a column that participates in a foreign-key definition — it requires a full table rebuild. With real FKs the migration could not be rolled back on the engine the entire test suite runs on. The referenced rows are catalogue rows that the platform deactivates rather than deletes; integrity is enforced by the Form Request `exists:` rule, and a dangling id degrades to "no preference" because the matching relation resolves to `null`. §8.2/§8.5 are superseded by this note. |
| **D2** | The `options` prop was moved from the recommendations page to the profile editor.                                                                                                             | The option lists exist to render the preference selects, which live on the profile editor. Shipping them on the recommendations page would have been unused payload.                                                                                                                                                                                                                                                                                                                                                        |
| **D3** | The candidate dashboard entry is a **link card**, not a three-row inline preview.                                                                                                             | An inline preview would add a recommendation query to the dashboard hot path, which §13.2 flags as a risk. The link keeps the dashboard free of the extra query.                                                                                                                                                                                                                                                                                                                                                            |
| **D4** | The candidate's canonical skill set is derived from `candidate_profiles.skills` at read time; the `candidate_skills` table is maintained by `SkillIndexService` but is not read by the query. | Profiles created before this feature have a populated `skills` column but no pivot rows. ### 16.3 Defects found during implementation and fixed

1. **The skill index was never written.** `Job::saved` / `CandidateProfile::saved` were gated on `wasChanged('skills')`, which Laravel never reports for an insert. Both pivot tables were empty for every newly created record. Found with a temporary probe test, fixed by moving to the `created`/`updated` events (D5).
2. **The preference validator never ran.** The `withValidator` callback that checks the experience dates returned early when `experiences` was not submitted, which skipped the new preference checks as well. The two checks are now separate `after` callbacks.
3. **A rewrite dropped an existing validation.** Rewriting `UpdateCandidateProfileRequest` changed `$normalizedRows[$index]` to `$normalizedRows[]` and removed the existing `is_current`/`end_date` validator. Caught by diffing against `HEAD` and restored.
4. **`CandidateProfile` lost its `user()` docblock line** in a rewrite. Restored.
5. **Distinct experience levels were reported as the same band** (reported by the user). The scorer compared `experience_levels.sort_order` directly. That column is not unique — the admin form accepts any integer in `0–9999` and the factory defaults to `0` — so levels named "1 year", "2 year" and "3 year" that were all left at the default order compared as equal. A candidate targeting "3 year" saw a "1 year" role highlighted as _"matches your target level"_, and the level signal contributed 20 points it had not earned. Reproduced with a failing test (two distinct levels sharing `sort_order = 0` scored 100 with an `experience_level_match` reason), then fixed by comparing a unique band rank derived from `(sort_order, id)` (D9). Regression tests were added at both the unit and feature level.

### 16.4 Performance verification (EXPLAIN) — recorded

Measured on **SQLite** (the engine the test suite runs on) against a seeded dataset of
**100 companies / 3 000 published jobs / 24 000 `job_skills` rows**, with one candidate
holding 4 skills, 1 preferred category, 1 preferred workplace, 1 target level and a location.

- **13 queries** for a full recommendations request. No N+1.
- **53.6 ms** end to end; the pool query itself **7 ms**.
- The band-ranking query added by D9 is `select id from experience_levels order by sort_order asc, id asc` — a scan of a table that holds roughly ten rows, with a temp b-tree for the sort. It replaced the previous `whereIn(sort_order, ...)` query, so the request query count is unchanged.
- Pool query plan:

```text
SEARCH job_postings USING INDEX job_postings_status_created_at_index (status=?)
CORRELATED SCALAR SUBQUERY -> SEARCH job_skills USING INDEX job_skills_posting_skill_unique (job_posting_id=? AND skill=?)
SEARCH companies EXISTS USING INTEGER PRIMARY KEY (rowid=?)
CORRELATED SCALAR SUBQUERY -> SEARCH users USING INTEGER PRIMARY KEY (rowid=?)
CORRELATED SCALAR SUBQUERY -> SEARCH job_skills USING COVERING INDEX job_skills_posting_skill_unique (job_posting_id=?)
USE TEMP B-TREE FOR LAST TERM OF ORDER BY
```

- The matched-skill eager load uses **`job_skills_skill_posting_idx (skill=? AND job_posting_id=?)`** ✅ — the index added by this feature is used.
- `job_postings_location_city_idx`, `job_postings_category_id_idx`, `job_postings_experience_level_id_idx` and `job_postings_workplace_arrangement_id_idx` exist and are available to the filter terms; the planner chose `job_postings_status_created_at_index` for the driving scan because the `status = 'published'` term is the most selective in this dataset.
- The `USE TEMP B-TREE FOR LAST TERM OF ORDER BY` is the `created_at, id` tie-break; it is bounded by the 200-row pool.

**Pool saturation: 1 500 %.** With 3 000 published jobs and broad candidate preferences, **all
3 000** jobs matched at least one stated signal while the pool cap is 200. The ranking is
therefore _fit-first within the 200 newest matching jobs_, and strong matches published long
ago fall outside the pool. **This meets the trigger condition for follow-up F1** (§15). F1 was
left unimplemented because changing the pool ordering is a design change to the approved
specification, and it would either move scoring into SQL (risking the reason/score agreement
guarantee) or introduce a partial fit proxy. The measurement is recorded here for an explicit
decision.
