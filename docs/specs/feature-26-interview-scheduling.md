# Feature 26 — Interview scheduling

## Metadata

- **Feature ID**: Feature 26
- **Title**: Interview scheduling
- **Source**: `project-overview.md` (Feature 26)
- **Dependencies**: Feature 23 (employer applicant detail), Feature 24 (status transitions), Feature 25 (notifications)
- **Status**: DRAFT — awaiting approval
- **Baseline**: repository clean on `main`; Feature 25 committed; full suite currently **389 passing / 2791 assertions**.

---

## Goal

Let an approved employer owning a company schedule multiple interview rounds for an application to one of that company's jobs, reschedule or cancel individual rounds, and see candidate responses. Let the applying candidate view every round, accept, decline, or request a new time with a proposed alternative. Persist all instants in UTC, preserve the employer-selected IANA display time zone, notify the other party through the existing in-app notification system, and return the application to `shortlisted` when the last active interview is cancelled.

## Non-goals

- External calendar integration (Google/Outlook), ICS files, or calendar invites.
- Integrated video calls, platform-generated meeting rooms, or real-time chat.
- Email/SMS/push notifications.
- Candidate self-booking against an availability calendar.
- Interview feedback, scoring, completion tracking, or offer management.
- A full append-only interview audit timeline; current state plus response/cancellation metadata is stored. Audit-grade history is deferred to Feature 31.
- Company-team membership; interviews remain company-owner-only until Feature 28.
- Automated scheduling, time-slot proposals generated by the platform, or multi-slot polls.

## Actors and user flows

### Employer (approved company owner)

1. Opens an application detail page at `/employer/applications/{application}`.
2. Sees a paginated list of interview rounds, newest first, with the current/upcoming round visually distinguished.
3. Schedules a new round by entering local date/time, IANA time zone, duration, mode (`online`, `onsite`, `phone`), location/meeting details, candidate instructions, and optional employer-only internal notes.
4. If the application is `shortlisted`, the first scheduled round moves it to `interview_scheduled` and records status history. Additional rounds keep it at `interview_scheduled`.
5. Can reschedule or cancel an active round. Rescheduling resets that round to `scheduled` and re-notifies the candidate. Cancellation requires a reason.
6. Sees candidate responses: accepted, declined, or a request for a new time with the candidate's proposed instant/note.
7. May schedule another round after a decline or after the last round is cancelled.

### Candidate (job seeker)

1. Opens their application detail page at `/candidate/applications/{application}`.
2. Sees every interview round for that application, paginated newest first, with status and candidate-safe details.
3. For a `scheduled` round, can accept, decline, or request a new time by proposing one local date/time, an IANA time zone, and an optional note.
4. Sees the employer-selected time zone and, when different, their own browser-local time.
5. Never sees employer `internal_notes`.

### Notification recipients

- Candidate: interview scheduled, rescheduled, or cancelled.
- Company owner: candidate accepted, declined, or requested a new time.
- Notification text never contains `internal_notes`, and does not repeat detailed meeting/access instructions beyond the job title and time.

## Assumptions and product decisions

1. **A1 — Multiple interview rounds are supported.** There is no unique constraint on `job_application_id`. Each round is its own `interviews` row. There is no hard-coded maximum; the embedded list is paginated.
2. **A2 — One proposed alternative per request.** A candidate reschedule request includes one proposed local instant, an IANA zone, and an optional note. Multi-slot polls are deferred.
3. **A3 — Application coupling.** Scheduling from `shortlisted` transitions the application to `interview_scheduled` and records history. Scheduling further rounds from `interview_scheduled` does not add duplicate status history.
4. **A4 — Last cancellation reverts the application.** When the last active interview is cancelled, the application returns to `shortlisted` through a **system-only** transition with status history. This transition is not added to the employer's manual status dropdown, so a recruiter cannot bypass the interview guard by selecting it directly. "Active" means `scheduled`, `accepted`, or `reschedule_requested`; `declined` and `cancelled` are inactive.
5. **A5 — Declining does not revert.** If the candidate declines the last active round, the application remains `interview_scheduled`; the employer can schedule a new round or use the existing manual transition controls to move to `offer_sent`/`rejected`. Only cancellation triggers the automatic `shortlisted` revert.
6. **A6 — Application status is authoritative.** Scheduling is allowed only when the application is `shortlisted` or `interview_scheduled`. If the application leaves `interview_scheduled` for `offer_sent`, `rejected`, or `withdrawn`, all active interviews are automatically cancelled.
7. **A7 — Time zone model.** `scheduled_at` is stored as UTC. `timezone` stores the employer-selected IANA zone. `requested_scheduled_at` is stored as UTC with `requested_timezone` for a candidate proposal. Browser-local time is derived for display; no user time-zone preference is added.
8. **A8 — No new permissions.** Access is company-owner/candidate ownership checked by a new `InterviewPolicy`, consistent with Features 23–24. Feature 28 can later replace owner checks with company-scoped membership.
9. **A9 — Interview mode is descriptive.** `online` means the employer supplies meeting/connection details as text; the platform does not generate or verify a video room.
10. **A10 — Notifications are synchronous**, created after the primary transaction through the existing `NotificationService` try/catch + `Log::warning` pattern.
11. **A11 — No separate interview page.** Interview rounds are embedded in the existing application detail pages with their own `interview_page` query parameter and pagination. This avoids a second set of detail pages while keeping the list bounded.
12. **A12 — No completed status.** Interview completion tracking is deferred. Past rounds remain in their last response state for display.
13. **A13 — No overlapping active rounds.** Scheduling, rescheduling, or proposing a time that overlaps another active round for the same application is rejected with a validation error. Availability calendars remain out of scope; this is a simple interval guard, not a scheduling engine.

No blocking questions remain after the approved product decisions. The assumptions above are design-level refinements.

## User-visible acceptance criteria

- [ ] An approved employer who owns the application's job company can schedule multiple interview rounds; unrelated, unapproved, or non-owner employers receive 403.
- [ ] Scheduling requires a future date/time, valid IANA time zone, duration, mode, and location/meeting details; invalid input returns field errors and creates no partial record.
- [ ] The first schedule from `shortlisted` records a transition to `interview_scheduled`; additional rounds do not duplicate status history.
- [ ] Interview rounds are paginated on both application detail pages and are limited to the application owner/authorized employer.
- [ ] The candidate can accept, decline, or request a new time for their own `scheduled` round; other candidates and employers receive 403.
- [ ] A schedule, reschedule, or proposed time that overlaps another active round's interval is rejected with a field error; no overlapping active rounds are ever created.
- [ ] A reschedule request stores the proposed UTC instant, proposed IANA zone, and optional note; the employer sees them and the candidate sees them.
- [ ] The employer can reschedule or cancel an active round only for their company's application; stale form state returns 409 and changes nothing.
- [ ] Rescheduling an active round resets it to `scheduled`, clears prior response/request metadata, and re-notifies the candidate.
- [ ] Cancelling an active round requires a reason and notifies the candidate; the reason is visible to the candidate.
- [ ] Cancelling the last active round returns the application to `shortlisted` and records status history; cancelling one of several active rounds leaves the application at `interview_scheduled`.
- [ ] The system-only `interview_scheduled → shortlisted` transition is not exposed in the normal employer transition dropdown.
- [ ] Declining the last active round does not automatically revert the application.
- [ ] Candidate props never include `internal_notes`; employer props include them.
- [ ] Notification payloads contain no internal notes or private access details.
- [ ] Date/time displays correctly in the stored time zone and in the viewer's local time zone when different.
- [ ] Empty, processing, validation-error, stale-update, and paginated states are clear and accessible.

## Form Requests and validation

### `StoreInterviewRequest`

- **authorize()**: `createForApplication` on the bound application.
- **Input**: `scheduled_at_local` (`Y-m-d\TH:i`), `timezone` (IANA), `duration_minutes`, `mode`, `location_details`, `candidate_instructions`, `internal_notes`.
- **prepareForValidation()**:
    - Trim strings; normalize empty optional fields to `null`.
    - Reject malformed local time or invalid time zone without throwing.
    - Convert local wall time in the selected timezone to UTC with `CarbonImmutable::createFromFormat('!Y-m-d\TH:i', ..., $timezone)->utc()`.
    - Always overwrite a server-only `scheduled_at_utc` field; never trust a client-supplied UTC value.
- **Rules**:
    - `scheduled_at_local`: required, `date_format:Y-m-d\TH:i`.
    - `timezone`: required, Laravel `timezone` rule (valid IANA identifier).
    - `scheduled_at_utc`: required, date, **after now** (server-computed).
    - `duration_minutes`: required integer, 15–480.
    - `mode`: required, `Rule::enum(InterviewMode::class)`.
    - `location_details`: required string, max 500.
    - `candidate_instructions`: nullable string, max 2000.
    - `internal_notes`: nullable string, max 2000.
- **Custom messages**: future-time, invalid-timezone, and invalid-local-time errors should name the date/time fields rather than expose `scheduled_at_utc`.

### `UpdateInterviewRequest` (reschedule an active round)

- Same schedule fields and timezone conversion as `StoreInterviewRequest`.
- Adds concurrency fields:
    - `current_status`: required, `Rule::enum(InterviewStatus::class)`.
    - `current_scheduled_at`: required ISO-8601 UTC timestamp from the page prop.
- Service locks the interview, requires an active interview status and an `interview_scheduled` application, compares status/schedule, and returns 409 on mismatch.
- Cancelled/declined rounds are not reopened; the employer schedules a new round instead.

### `CancelInterviewRequest`

- **authorize()**: `manage` on the interview.
- `current_status`: required, valid `InterviewStatus`.
- `current_scheduled_at`: required ISO-8601 UTC timestamp from the page prop.
- `cancellation_reason`: required string, 3–500.
- Service allows cancellation only from `scheduled`, `accepted`, or `reschedule_requested`; otherwise 422. Status/time mismatch returns 409.

### `RespondToInterviewRequest`

- **authorize()**: `respond` on the interview.
- `current_status`: required, valid `InterviewStatus`.
- `current_scheduled_at`: required ISO-8601 UTC timestamp from the page prop.
- `response`: required, one of `accepted`, `declined`, `reschedule_requested`.
- Conditional fields when requesting a new time:
    - `requested_at_local`: required, `date_format:Y-m-d\TH:i`.
    - `requested_timezone`: required, valid IANA zone.
    - `requested_at_utc`: server-computed, required when requesting, must be in the future.
    - `response_note`: nullable string, max 500.
- Accept/decline clear any previous proposed-time fields.
- Service locks the interview, requires current status `scheduled`, compares the schedule timestamp, and returns 409/422 on stale or repeated responses.

All write endpoints use Form Requests; no inline controller validation and no reliance on request payloads for `user_id`, `job_application_id`, `scheduled_by_id`, or `status`.

## Data model, migration, foreign keys, indexes

### `interviews`

```php
Schema::create('interviews', function (Blueprint $table): void {
    $table->id();
    $table->unsignedBigInteger('job_application_id');
    $table->foreignId('scheduled_by_id')->nullable()->constrained('users')->nullOnDelete();
    $table->dateTime('scheduled_at');
    $table->unsignedSmallInteger('duration_minutes');
    $table->string('timezone', 64);
    $table->string('mode', 20);
    $table->string('location_details', 500);
    $table->text('candidate_instructions')->nullable();
    $table->text('internal_notes')->nullable();
    $table->string('status', 20)->default('scheduled');
    $table->dateTime('responded_at')->nullable();
    $table->dateTime('requested_scheduled_at')->nullable();
    $table->string('requested_timezone', 64)->nullable();
    $table->string('response_note', 500)->nullable();
    $table->dateTime('cancelled_at')->nullable();
    $table->text('cancellation_reason')->nullable();
    $table->timestamps();

    $table->index(['job_application_id', 'created_at'], 'interviews_application_created_idx');
    $table->foreign('job_application_id')->references('id')->on('job_applications')->cascadeOnDelete();
});
```

- **Multiple rounds**: no unique constraint on `job_application_id`.
- **Composite index**: `(job_application_id, created_at)` supports the paginated "rounds for this application, newest first" query and also provides the leftmost `job_application_id` index required by the foreign key. Verify with `SHOW INDEX` that the FK does not create a duplicate standalone index; define the composite index before the FK if the driver requires it.
- **UTC wall-clock storage**: use `dateTime` (not MySQL `TIMESTAMP`) for `scheduled_at`, response/request/cancellation instants. The app timezone is UTC and the MySQL session timezone is not explicitly configured, so `dateTime` avoids implicit session-timezone conversion. Carbon writes/reads the UTC wall clock; display conversion happens explicitly with the stored IANA zone.
- **Other FKs**: `scheduled_by_id` is nullable `nullOnDelete`; keep its FK index and do not add a redundant duplicate.
- **No `status` index** until a query needs it. The embedded list is scoped by application; there is no global upcoming-interview list.

### Enums

- `app/Enums/InterviewStatus.php`: `scheduled`, `accepted`, `declined`, `reschedule_requested`, `cancelled` with `label()`, `isActive()` (`scheduled`/`accepted`/`reschedule_requested`), and small state helpers used by the service. Candidate UI may render `scheduled` as “Awaiting your response”.
- `app/Enums/InterviewMode.php`: `online`, `onsite`, `phone` with `label()`.

### Models

- `app/Models/Interview.php`: `$fillable` for mapped fields only; casts for `scheduled_at`, `responded_at`, `requested_scheduled_at`, `cancelled_at` (`datetime`), `status` (`InterviewStatus`), `mode` (`InterviewMode`), `duration_minutes` (`integer`).
- `Interview::jobApplication(): BelongsTo` and `Interview::scheduledBy(): BelongsTo`.
- `JobApplication::interviews(): HasMany` ordered by `created_at` in the controller query, not in the relationship, so pagination is explicit.
- `database/factories/InterviewFactory.php` with sensible UTC defaults and states for each status.

### Data ownership / invariants

- `scheduled_by_id` comes from the authenticated employer, never the request.
- `status` is server-controlled; create/update forms cannot submit `accepted`, `declined`, `reschedule_requested`, or `cancelled`.
- `internal_notes` is employer-only and must never be included in candidate props or notifications.
- `requested_scheduled_at`/`requested_timezone`/`response_note` are written only by the candidate response flow.

## Service / Repository decision

Add `app/Services/InterviewService.php`.

Justification: scheduling is a multi-step, transactional operation that locks the application, creates/updates interviews, enforces a state machine, coordinates candidate proposals, and couples to the existing application status transition service. It is reused by employer schedule/reschedule/cancel actions and candidate responses. This is not simple single-use CRUD.

No Repository is added: queries are simple application-scoped relation lookups and locked row reads, and the codebase does not use repositories for comparable workflows.

### Lock order

All mutations lock the `job_applications` row first, then the relevant `interviews` row(s). This prevents deadlocks between scheduling (application first) and cancellation/revert (application status update plus interview change).

### Service methods

1. `schedule(JobApplication $application, User $actor, array $data): Interview`
    - `DB::transaction`; lock the application row with `lockForUpdate()`.
    - Re-read status. Allow `shortlisted` or `interview_scheduled`.
    - Check the new interval `[scheduled_at, scheduled_at + duration_minutes)` against every other active round for the same application (`scheduled`, `accepted`, `reschedule_requested`). Overlap → throw `ValidationException` on `scheduled_at_local`.
    - Create a new interview row from validated mapped data. Multiple non-overlapping rounds are allowed.
    - If status was `shortlisted`, call `ApplicationStatusTransitionService::transitionAsEmployer(..., InterviewScheduled, 'shortlisted', $actor, 'Interview scheduled')` so history is recorded. If already `interview_scheduled`, skip.
2. `update(Interview $interview, User $actor, array $data): Interview`
    - Lock application then interview.
    - Require application status `interview_scheduled`.
    - Require interview status in `scheduled`, `accepted`, or `reschedule_requested`.
    - Compare `current_status` and `current_scheduled_at`; mismatch → 409.
    - Check the new interval against every other active round, excluding this one. Overlap → `ValidationException` on `scheduled_at_local`.
    - Update schedule/details, set status `scheduled`, clear `responded_at`, `requested_scheduled_at`, `requested_timezone`, `response_note`, `cancelled_at`, `cancellation_reason`; set `scheduled_by_id = actor`.
3. `cancel(Interview $interview, User $actor, string $reason): Interview`
    - Lock application then interview.
    - Require application status `interview_scheduled`.
    - Require interview status in `scheduled`, `accepted`, or `reschedule_requested`.
    - Compare `current_status` and `current_scheduled_at`; mismatch → 409.
    - Set `cancelled`, `cancelled_at`, `cancellation_reason`.
    - If no other interview for the application is in an active status, call `ApplicationStatusTransitionService::revertToShortlistedAfterLastInterviewCancellation($application, $actor, 'Last interview cancelled.')`.
    - If other active rounds remain, leave the application at `interview_scheduled`.
4. `respond(Interview $interview, User $candidate, array $data): Interview`
    - Lock application then interview.
    - Require application status `interview_scheduled`.
    - Require current interview status `scheduled`.
    - Compare `current_status` and `current_scheduled_at`; mismatch → 409.
    - For `accepted`/`declined`: set status, `responded_at`, optional `response_note`; clear requested-time fields.
    - For `reschedule_requested`: require the server-computed future `requested_at_utc` and `requested_timezone`; check the proposed interval (using this round's `duration_minutes`) against every other active round (excluding this one), rejecting overlap with `ValidationException`; set status `reschedule_requested`, `responded_at`, proposed-time fields, and optional note.
    - Application status is unchanged.

Overlap is a simple half-open interval comparison in UTC and is evaluated inside the application-locked transaction, so concurrent requests cannot create overlapping active rounds. Cancelled and declined rounds are ignored.

Controllers call the service, then call `NotificationService` after the service returns. The service does not dispatch notifications itself, matching the Feature 24/25 pattern.

### System-only application revert

Add `ApplicationStatusTransitionService::revertToShortlistedAfterLastInterviewCancellation(JobApplication $application, User $actor, string $reason): JobApplication`.

- Lock the application; require `interview_scheduled`.
- Verify no interview remains in `scheduled`, `accepted`, or `reschedule_requested`.
- Create a `job_application_status_histories` row from `interview_scheduled` to `shortlisted` with the actor and reason.
- Set the application status to `shortlisted`.
- Do **not** add `shortlisted` to `JobApplicationStatus::allowedEmployerTransitions()` for `interview_scheduled`; the normal employer dropdown remains unchanged. This is a guarded system transition, tested separately.

### Avoiding a service dependency cycle

`InterviewService` uses `ApplicationStatusTransitionService` for scheduling and the last-cancellation revert. `ApplicationStatusTransitionService` must not depend on `InterviewService`. When an application leaves `interview_scheduled` for `offer_sent`, `rejected`, or `withdrawn`, that service performs a focused cancellation inside its existing transaction:

```php
$application->interviews()
    ->whereIn('status', [
        InterviewStatus::Scheduled->value,
        InterviewStatus::Accepted->value,
        InterviewStatus::RescheduleRequested->value,
    ])
    ->update([
        'status' => InterviewStatus::Cancelled->value,
        'cancelled_at' => now(),
        'cancellation_reason' => 'Application moved to '.$newStatus->label().'.',
    ]);
```

This is a deliberate small duplication of cancellation state rather than a circular service dependency. The interview service remains the authority for normal employer cancel/reschedule requests.

## Application lifecycle integration

- Scheduling from `shortlisted` records `shortlisted → interview_scheduled` history. Additional rounds do not duplicate it. Only the interview notification is sent; no duplicate status notification.
- When an employer moves an application from `interview_scheduled` to `offer_sent` or `rejected`, or a candidate withdraws, cancel all active interviews in the same transaction with a system reason. These lifecycle-driven cancellations do not send a separate interview notification; the existing status/withdrawal notification is authoritative.
- Cancelling the last active round records `interview_scheduled → shortlisted` history and returns the application to the recruiter's shortlist.
- Cancelling one of several active rounds keeps the application at `interview_scheduled`.
- Declining a round, including the last active round, does not change application status.
- Existing Feature 24 manual transition rules remain unchanged; this feature adds only the guarded system revert.

- Notification creation happens after the service transaction and remains wrapped by `NotificationService` failure logging.

### Validation

- Past date/time → 422, no row.
- Invalid IANA timezone → 422.
- Malformed `scheduled_at_local` → 422.
- Missing/too-short/too-long `location_details`; invalid mode; duration below 15 or above 480 → 422.
- Missing cancellation reason or reason too short/long → 422.
- Invalid candidate response value → 422.
- Reschedule request missing proposed time/zone or with a past proposed time → 422.
- Schedule/reschedule interval overlapping another active round → 422; adjacent (touching, non-overlapping) intervals are allowed.
- Candidate-proposed time overlapping another active round → 422.
- Cancelled/declined rounds do not block a new overlapping round.
- Optional blanks are normalized to `null`.
- DST boundary conversion is covered (for example, a US zone around a transition) without accepting a wrong UTC instant.
- Time-sensitive tests freeze the clock with `Carbon::setTestNow()` to avoid flakiness.

### Authorization and ownership

- Guest is redirected from employer and candidate interview routes.
- Candidate cannot access employer schedule/update/cancel routes.
- Employer cannot access candidate respond route.
- Unrelated approved employer gets 403 for another company's interview.
- Unapproved employer with `employer` role gets 403/redirect per `employer.approved`.
- Another candidate cannot respond to or view another candidate's interview.
- Cross-company guessed application/interview IDs do not leak interview data.

### State and concurrency

- Schedule from `submitted`, `reviewing`, `offer_sent`, `hired`, `rejected`, or `withdrawn` → 422.
- Reschedule/cancel with stale `current_status` or `current_scheduled_at` → 409, no change.
- Reschedule/cancel a cancelled or declined round → 422.
- Respond twice, respond after cancel, or respond after the application left `interview_scheduled` → 409/422.
- Candidate withdrawal cancels all active interviews.
- Employer transition from `interview_scheduled` to `offer_sent`/`rejected` cancels all active interviews.
- Cancelling the only active round → application `shortlisted`, system history row recorded.
- Cancelling one of several active rounds → application remains `interview_scheduled`.
- Declining the last active round → application remains `interview_scheduled`.
- Scheduling a new round after the last cancellation re-enters `interview_scheduled` and records history.
- The manual employer transition list still does not include `shortlisted` from `interview_scheduled`.

- Correct recipients only (candidate for schedule/reschedule/cancel; owner for accept/decline/request).

## Security and performance risks

- **IDOR / cross-company access**: route binding alone is insufficient; every mutation authorizes through `InterviewPolicy`. Tests cover guessed IDs and unrelated employers/candidates.
- **Mass assignment**: only mapped validated fields are written; actor, application, status, and timestamps are server-derived.
- **Sensitive data leakage**: `internal_notes` must never reach candidate props/notifications; meeting details are intentionally candidate-visible but excluded from notification text. No `SELECT *` in mapped queries.
- **State tampering**: clients cannot set `accepted`/`declined`/`reschedule_requested`/`cancelled` on create, cannot set application status, and cannot bypass service state checks.
- **Concurrency**: application-first lock order, status/schedule comparison, and transactional last-cancellation revert prevent stale overwrites and inconsistent application/interview state.
- **Time-zone correctness**: UTC storage, IANA validation, server-side conversion, and dual-zone display. Do not infer a time zone from free text.
- **Notification failure isolation**: existing `NotificationService` try/catch keeps the interview write intact.
- **XSS**: all free-text instructions/notes/notes render as escaped text; no HTML rendering.
- **Performance**: one bounded paginator query per application detail, explicit selected columns, no N+1, no unbounded relation load.
- **Retention**: interviews cascade with application deletion and are retained when cancelled/declined; no delete route.
