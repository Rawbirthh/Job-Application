## Goal

Provide a reliable, persisted in-app notification center where each user can see, read, and manage notifications generated by important product events. Notifications are created for selected events (application submission confirmation, new application received by employer, job submitted for review, application status changes, candidate withdrawal, employer job moderation outcomes, new user registration, and employer onboarding submission), persist read/unread state, and are strictly scoped to their recipient.

## Non-Goals

- Email, SMS, push, or real-time WebSocket delivery (deferred).
- Notification preferences, digest scheduling, or user-configurable channels.
- Admin broadcast/announcement notifications (only the event-driven admin notifications listed in scope are included).
- Deletion of notifications (read/unread state only).
- Automated/AI screening or ranking notifications.
- Company-team (Feature 28) recipient resolution beyond the company owner.

## Actors and Flows

### 1. Any authenticated user (candidate, employer, platform admin)

- Sees an unread count badge in the shared app shell (header/sidebar).
- Navigates to `/notifications` to view a paginated list of their notifications, newest first.
- Clicks a notification to open its linked record (when a URL is present).
- Marks a single notification as read via `PATCH /notifications/{notification}/read`.
- Marks all unread notifications as read via `POST /notifications/read-all`.
- Unread notifications are visually distinguished; read notifications remain in history.

### 2. Candidate (job seeker)

- Receives a notification when their application is successfully submitted (confirmation).
- Receives a notification when an employer transitions their application status.
- Does not receive a notification for their own withdrawal (they initiated it).

### 3. Employer (approved company owner)

- Receives a notification when a candidate withdraws an application for one of their company's jobs.
- Receives a notification when an admin approves or rejects one of their company's job postings.
- Does not receive a notification for status changes they initiate (they are the actor).

### 4. Platform admin

- Receives a notification when a new user registers publicly.
- Receives a notification when a user submits an employer onboarding request.
- Admin actions (job moderation) generate notifications to employers; admins themselves are not notified of their own actions.

## User-Visible Behavior and Acceptance Criteria

- [ ] Authenticated user can open `/notifications` and see only their own notifications, newest first, paginated.
- [ ] Each notification shows title, message, created time, read/unread state, and optional link.
- [ ] `PATCH /notifications/{notification}/read` marks one notification as read; only the owner may do this (others receive 403).
- [ ] `POST /notifications/read-all` marks all of the current user's unread notifications as read.
- [ ] Unread count badge in the shared shell reflects the current user's unread count.
- [ ] Application submission creates a confirmation notification for the candidate.
- [ ] Employer status transition creates a status-change notification for the candidate.
- [ ] Candidate withdrawal creates a notification for the company owner.
- [ ] Admin approve/reject of a job creates a moderation-outcome notification for the company owner.
- [ ] New user registration creates a notification for platform administrators (users with role `platform_admin`).
- [ ] Employer onboarding submission creates a notification for platform administrators (users with permission `employers.view` or role `platform_admin`).
- [ ] Notification creation failures are logged and do not roll back or fail the primary business operation.
- [ ] No notification exposes sensitive internal notes, candidate private data beyond what the recipient is authorized to see, or another user's notifications.
- [ ] Empty state is shown when the user has no notifications.

## Assumptions / Questions

### Assumptions (non-blocking)

1. **A1**: Laravel's database notification channel and `notifications` table are used; `User` already uses the `Notifiable` trait.
2. **A2**: Notifications are created synchronously (not queued) so they are immediately visible; the database write is small and transactional safety is handled by wrapping in try/catch + logging.
3. **A3**: Recipients are resolved as follows:
    - Application submitted event: candidate (`JobApplication.user`) and company owner (`Job.company.owner`).
    - Application status/withdrawal events: candidate for status changes; company owner for withdrawals.
    - Job submitted for review event: users with both `admin.access` and `jobs.moderate` permissions (this includes platform admins).
    - Job moderation events: company owner (`Job.company.owner`).
4. **A4**: Notification content stores a server-generated relative URL string for navigation; the frontend uses Inertia navigation.
5. **A5**: No new permissions are introduced; access is based on ownership (`notifiable_id` + `notifiable_type = User`).
6. **A6**: Read state uses Laravel's `read_at` timestamp; unread means `read_at IS NULL`.
7. **A7**: Platform administrators are resolved as users holding role `platform_admin` (see `RoleSlug::PlatformAdmin`). If none exist, the notification is skipped (no error).
8. **A8**: Admin notifications for new registrations and onboarding submissions are created synchronously after the primary write succeeds, using the same try/catch + logging pattern.

### Focused questions (blocking only if product disagrees)

1. **Q1**: Should employers also receive a "new application received" notification on submission, or is candidate confirmation only in scope? **Assumption A3 says candidate confirmation only**; change if product wants employer notification.
2. **Q2**: Should notifications be deletable by the recipient? **Assumption: no**, only read/unread.
3. **Q3**: Should admin users receive notifications for moderation actions performed by other admins? **Assumption: no**.

If these assumptions are acceptable, no answers are required to proceed.

## Routes and Access Boundary

All routes are inside the existing `auth` middleware group in `routes/web.php`. No role/permission middleware is added because notifications are strictly owner-scoped; authorization is enforced by `NotificationPolicy`.

```php
Route::middleware(['auth'])->group(function (): void {
    // ... existing routes ...

    Route::get('notifications', [NotificationController::class, 'index'])
        ->name('notifications.index');

    Route::patch('notifications/{notification}/read', [NotificationController::class, 'markAsRead'])
        ->name('notifications.read');

    Route::post('notifications/read-all', [NotificationController::class, 'markAllAsRead'])
        ->name('notifications.read-all');
});
```

Notes:

- `notifications/read-all` must be registered before `notifications/{notification}/read`? Static path is distinct (different segment count), but keep static-ish route first for clarity.
- Throttling: reuse `throttle:30,1` on write endpoints to prevent abuse.
- Wayfinder route helpers are regenerated by the frontend build; rebuild after route changes.

## Policy Actions and Dynamic Role/Permission Resolution

Create `App\Policies\NotificationPolicy` for `Illuminate\Notifications\DatabaseNotification`.

```php
public function view(User $user, DatabaseNotification $notification): bool
{
    return $notification->notifiable_type === User::class
        && (int) $notification->notifiable_id === $user->id;
}

public function update(User $user, DatabaseNotification $notification): bool
{
    return $this->view($user, $notification);
}
```

Controller calls `$this->authorize('view', $notification)` before mark-as-read. Mark-all-read operates only on the authenticated user's notifications and needs no model authorization.

No new roles/permissions are introduced.

## Data Model, Migration, Constraints, and Indexes

### Migration: `notifications` table

Use Laravel's standard database notification schema, with an added composite index for unread queries.

```php
Schema::create('notifications', function (Blueprint $table): void {
    $table->uuid('id')->primary();
    $table->string('type');
    $table->morphs('notifiable'); // notifiable_type, notifiable_id + index
    $table->text('data');
    $table->timestamp('read_at')->nullable();
    $table->timestamps();

    $table->index(['notifiable_id', 'read_at']);
});
```

Notes:

- `morphs('notifiable')` already creates an index on `(notifiable_type, notifiable_id)`.
- The additional `(notifiable_id, read_at)` index supports `WHERE notifiable_id = ? AND read_at IS NULL` (unread count/list). Leftmost prefix covers `notifiable_id` alone.
- No foreign key constraint is added to `notifiable_id` because Laravel's notification system uses a polymorphic relation; ownership is enforced in application code and Policy.
- Down migration drops the table.

### Model usage

Use Laravel's `Illuminate\Notifications\DatabaseNotification` directly (no custom model) via `User::notifications()` and `User::unreadNotifications()` provided by the `Notifiable` trait.

## Service / Repository Decision

**Decision**: Introduce `App\Services\NotificationService` as a single coordination point for creating notifications. Rationale:

- Notification creation is repeated across multiple controllers/services (apply, transition, withdraw, moderation).
- Centralizing try/catch + logging keeps failure handling consistent and testable.
- Keeps controllers thin and avoids scattering `User::notify()` calls.

**Not introducing a Repository**: Queries are simple (`$user->notifications()->latest()->paginate(15)` and `$user->unreadNotifications()->count()`). No complex multi-join/aggregate or reuse beyond one controller; inline queries in `NotificationController` are sufficient. No caching layer is added (scale not yet justified; unread count is a single indexed count).

### `NotificationService` API

```php
namespace App\Services;

class NotificationService
{
    public function applicationSubmitted(JobApplication $application): void;
    public function applicationStatusChanged(JobApplication $application, JobApplicationStatus $from, JobApplicationStatus $to): void;
    public function applicationWithdrawn(JobApplication $application): void;
    public function jobModerationOutcome(Job $job, bool $approved, ?string $reason = null): void;
    public function userRegistered(User $user): void;
    public function employerOnboardingSubmitted(User $applicant, EmployerOnboardingRequest $request): void;
}
```

Each method:

1. Resolves recipient(s).
2. Calls `$recipient->notify(new ...)` inside `try { ... } catch (\Throwable $e) { Log::warning('Notification creation failed', [...]); }`.
3. Never throws to the caller.

Call sites:

- `JobApplicationController::store`: after `JobApplication::create`, call `applicationSubmitted($application)`.
- `EmployerJobApplicationController::updateStatus`: capture `$from = $application->status` before service call; after successful transition call `applicationStatusChanged($application, $from, $newStatus)`.
- `ApplicationHistoryController::withdraw`: capture `$from = $application->status` before service call; after successful withdrawal call `applicationWithdrawn($application)`.
- `JobModerationController::approve`: after save, call `jobModerationOutcome($job, true)`.
- `JobModerationController::reject`: after save, call `jobModerationOutcome($job, false, $reason)`.
- `CreateNewUser::create`: after the transaction commits and the user is created (and role assigned), call `userRegistered($user)`. Notification creation must occur outside the DB transaction.
- `EmployerOnboardingController::store`: after `$this->employerOnboardingService->submit(...)` succeeds, call `employerOnboardingSubmitted($user, $user->employerOnboardingRequest)`.

Note: Notification creation happens after the primary DB write succeeds and outside the transition transaction (in controller) so a notification failure cannot roll back the business operation.

## React / Inertia Page, Form, and Component Plan

### Controller: `App\Http\Controllers\NotificationController`

```php
public function index(Request $request): Response
{
    $user = $request->user();

    $notifications = $user->notifications()
        ->latest()
        ->select(['id', 'type', 'data', 'read_at', 'created_at'])
        ->paginate(15)
        ->withQueryString();

    return Inertia::render('notifications/index', [
        'notifications' => $notifications->through(fn (DatabaseNotification $n): array => [
            'id' => $n->id,
            'type' => class_basename($n->type),
            'data' => $n->data ?? [],
            'read_at' => $n->read_at?->toIso8601String(),
            'created_at' => $n->created_at?->toIso8601String(),
        ]),
        'pagination' => [
            'current_page' => $notifications->currentPage(),
            'last_page' => $notifications->lastPage(),
            'per_page' => $notifications->perPage(),
            'total' => $notifications->total(),
            'prev_page_url' => $notifications->previousPageUrl(),
            'next_page_url' => $notifications->nextPageUrl(),
        ],
    ]);
}

public function markAsRead(DatabaseNotification $notification): RedirectResponse
{
    $this->authorize('view', $notification);

    if ($notification->read_at === null) {
        $notification->markAsRead();
    }

    $url = $notification->data['url'] ?? null;
    if (is_string($url) && $url !== '') {
        return redirect()->to($url);
    }

    return redirect()->back();
}

public function markAllAsRead(Request $request): RedirectResponse
{
    $request->user()->unreadNotifications()->update(['read_at' => now()]);
    return redirect()->back();
}
```

Notes:

- `markAsRead` redirects to the notification's URL when present, enabling click-through. If already read, still redirect.
- Use `Inertia::flash`? Not needed; redirect is enough.

## Risks, Rollout, and Compatibility Notes

- **Scale**: `notifications` table grows with usage. Indexes above support unread queries. Consider periodic pruning/archiving of read notifications in a later feature (Feature 31 audit log pattern). Not in scope here.
- **Idempotency**: Duplicate notifications are prevented by the idempotency of underlying operations (unique application per user/job; stale-update protection; status-gated moderation). If a controller is retried after a successful commit, the operation will fail before notification creation, preventing duplicates.
- **Failure isolation**: Notification creation is wrapped in try/catch and logged; primary operation remains successful. This may lead to missing notifications under DB issues; failures are observable via logs.
- **Queue**: Notifications are synchronous. If scale requires, convert notification classes to `ShouldQueue` later without changing call sites.
- **Migration**: New table; no changes to existing tables. Safe to deploy; rollback drops the table (loses notification history).
- **Frontend**: New page and shared prop; existing pages unaffected except unread badge in shared shell.
